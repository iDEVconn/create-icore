== CRITICAL BUG found during Task 13 live verification (not caught by any unit test, since tests mock document.cookie directly and never exercise real browser Path-scoping semantics) ==
Root cause: libs/shared/src/http/auth-cookies.ts's cookieOptions() applies the SAME path: '/api/auth' to BOTH icore_rt (httpOnly, correct) AND icore_csrf (must be JS-readable from any SPA route). Per RFC 6265, document.cookie only exposes a cookie on pages whose path is under the cookie's own Path — since the SPA's routes (/, /login, /dashboard, etc.) are never under /api/auth, readCsrfCookie() (libs/template-shared/src/lib/api/csrf.ts) ALWAYS returns null from real app pages, so X-CSRF-Token is never attached, verifyCsrf always fails server-side, and POST /auth/refresh always 403s.
Live-confirmed via Playwright against real dev servers (auth MS on FakeAuthStrategy fallback, gateway, client-shadcn): registered a user, logged in, confirmed localStorage has user-only (no tokens) — correct — then reloaded /dashboard and got redirected to /login with a live 403 on /auth/refresh in the console. This makes the ENTIRE feature non-functional: no authenticated user survives a page reload.
Ruling: icore_rt stays path: '/api/auth' (defense-in-depth, browser-managed, JS never touches it). icore_csrf must be path: '/' so JS can read it from any SPA route. The server-side verifyCsrf/readRefreshToken logic is unaffected (server-side cookie reads use req.cookies, populated by cookie-parser regardless of Path — Path only gates browser-side send/read behavior, not server parsing of an already-attached cookie). Dispatching a fix to Task 2's auth-cookies.ts + its tests, then re-verifying live.
