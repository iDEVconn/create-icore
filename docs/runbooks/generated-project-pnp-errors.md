# Runbook: Resolving Yarn PnP "tried to access <pkg>" in Generated Projects

## Symptoms

Running tasks (`yarn dev`, `yarn nx show projects`, `yarn build`, `yarn test`) in a project generated by `@idevconn/create-icore` fails with errors like:

```text
- apps/api/webpack.config.js:
    Error: Your application tried to access @nx/webpack, but it isn't declared in your dependencies;
    this makes the require call ambiguous and unsound.
    Required package: @nx/webpack (via "@nx/webpack/app-plugin")

- apps/client/vite.config.mts:
    [RESOLVE_ERROR] Could not resolve 'vite' in apps/client/vite.config.mts
    Your application tried to access vite, but it isn't declared in your dependencies...
```

## Root Cause

1. **Yarn 4 Default**: Without a `.yarnrc.yml` present at the root of the project declaring `nodeLinker: node-modules`, Yarn 4 defaults to **Plug'n'Play (PnP)** (`.pnp.cjs`).
2. **Missing Dotfiles in Published Tarball**: Earlier versions of the `@idevconn/create-icore` package (e.g. `0.20.0`) had dotfiles like `.yarnrc.yml`, `.gitignore`, and `.github/` omitted during `npm publish` because npm's pack mechanism ignores dotfiles.
3. **PnP Strict Isolation**: In Yarn PnP mode, each workspace package (`apps/api`, `apps/client`, `libs/shared`) is strictly isolated and cannot resolve devDependencies hoisted at the workspace root unless declared explicitly in the subproject's own `package.json`.
4. **Config vs manifest drift**: Generated `webpack.config.js`, `vite.config.mts`, and `vitest.config.mts` import tooling (`@nx/webpack`, `vite`, `vitest`, …) that was only listed in the root `package.json`, not in the owning workspace manifest.

## Permanent Solution (in `@idevconn/create-icore >= 0.20.1`)

1. **Underscore Prefixing**: Template dotfiles are now snapshotted and published as `_yarnrc.yml`, `_gitignore`, `_github/`, and `_husky/`.
2. **Restoration on Scaffold**: The `copyTree` function automatically restores these files to `.yarnrc.yml`, `.gitignore`, `.github/`, and `.husky/` during project generation.
3. **Safety Net**: If for any reason `.yarnrc.yml` is missing in a generated Yarn project, `scaffold()` synthesizes a minimal `.yarnrc.yml` with `nodeLinker: node-modules` and the detected Yarn release binary path before running install.
4. **Tarball Regression Guard**: CI runs `node tools/create-icore/scripts/check-tarball-dotfiles.mjs` to ensure required template dotfiles are always present in the packed npm tarball.
5. **Workspace ownership**: Every template workspace `package.json` now declares packages imported by its configs and source. `tools/create-icore/src/lib/__tests__/workspace-ownership.unit.test.ts` guards this in CI.
6. **Migration**: `create-icore migrate` runs the `pnp-workspace-dependencies` codemod to patch legacy projects (manifests + missing `.yarnrc.yml`).

## Immediate Workaround for Existing Projects

If you have an existing project affected by this issue, run the following commands in the root of the affected project:

```bash
# 1. Create .yarnrc.yml with node-modules linker
cat > .yarnrc.yml <<'EOF'
approvedGitRepositories:
  - "**"

enableGlobalCache: true
enableScripts: true
nodeLinker: node-modules
npmMinimalAgeGate: 0
yarnPath: .yarn/releases/yarn-4.18.0.cjs
EOF

# 2. Update packageManager in package.json
npm pkg set packageManager=yarn@4.18.0

# 3. Clean up PnP artifacts
rm -f .pnp.cjs .pnp.loader.mjs
rm -rf .yarn/unplugged .yarn/install-state.gz

# 4. Re-install with nodeLinker: node-modules
node .yarn/releases/yarn-4.18.0.cjs install

# 5. Reset Nx cache and verify
yarn nx reset
NX_DAEMON=false NX_ISOLATE_PLUGINS=false yarn nx show projects
```

## Related: a fixed CLI still produces a PnP project

Check `blueprint.json` in the generated project before debugging manifests.

- **`generatorVersion` is older than the fix.** `yarn create @idevconn/icore` resolves the npm registry (and Yarn's cache in `~/.yarn/berry/cache`), never your local checkout. Use `node <repo>/tools/create-icore/dist/cli.js <name> …` until the fix is published, then pin `@idevconn/icore@<version>`.
- **`packageManager` is not exactly `yarn`.** Before CLI flag validation, a typo such as `--package-manager=yarn.` was accepted, every `=== 'yarn'` branch in `scaffold.ts` went false, `.yarnrc.yml` and `.yarn/` were deleted, and a later `yarn install` fell back to PnP. Flags now go through `validateConfig(flags, 'flag')` and fail fast (`flag "packageManager" got "yarn.", expected one of: yarn, npm, pnpm`); unknown flags print a warning.
- **The first flag after `--` was lost.** `yarn create <pkg> <name> -- --db=sqlite …` forwards a literal `--`, which `parseFlags` consumed as a flag taking the next argument as its value. It is now skipped.

## Related: `api:build` TS2305 on `@icore/shared` with `--auth=none`

Symptom: `Module '"@icore/shared"' has no exported member 'InMemorySessionStore'` (also `RedisSessionStore`, `SessionStore`, `readSessionId`, `verifyCsrf`), and in the browser `readCsrfCookie` / `resolveEmailAction` missing from `@icore/template-shared`.

Cause: `applyAuthNoneVariants` overwrote both barrels with hardcoded strings that predated the session/cookie/CSRF exports. Fix: `pruneBarrel()` now starts from the template barrel and drops only `export … from` lines whose target was deleted by `AUTH_ONLY_PATHS` (the two `abilities` folders), so new template exports survive.

Test plan: `scaffold-auth-none.unit.test.ts` (`pruneBarrel`), `scaffold.unit.test.ts` and `scaffold.integration.unit.test.ts` (auth=none barrels keep session/hmac/csrf/auth exports and drop abilities), `prompts.unit.test.ts` (flag validation, `--` separator, unknown-flag warning). End-to-end: scaffold `--auth=none --db=sqlite --jobs=bullmq --transport=redis --ui=shadcn`, install on the Node version in `.nvmrc` (24), `nx run-many -t build` (7/7 green). `yarn dev` additionally needs Redis on `:6379` (`docker compose up -d redis`).

Note: install on Node 22.12 fails building `better-sqlite3`, because the hoisted `node-gyp@13` needs Node `^22.22.2 || ^24.15` and `undici@8` needs `>=22.19`. Use the `.nvmrc` version.
